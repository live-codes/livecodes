# Kotlin

[Kotlin](https://kotlinlang.org/) is a statically typed language that combines object-oriented and
functional programming. It targets the JVM, JavaScript and native platforms.

In LiveCodes, Kotlin source is compiled **in the browser** by the real K2 compiler, itself compiled
to WebAssembly. Nothing is sent to a server. The compiler can emit either
[JavaScript](#javascript-target) or [WebAssembly](#wasm-target); see [Targets](#targets).

:::info Note

The compiler is about 30 MB (compressed) and is downloaded on the first run, which can take some
time. It is cached by the browser afterwards. Libraries are fetched separately, only when a program
imports one.

:::

## Targets

The Kotlin compiler has two backends, chosen with the [`target`](#target) custom setting. They are
not interchangeable: each emits different output, and only the JavaScript target can use libraries
or the DOM.

| Target | The compiler emits | Runs as | Use for |
| --- | --- | --- | --- |
| `js` (default) | JavaScript, as a single self-contained ES module. | A plain script in the result page. | Anything that touches the DOM, and everything under [Libraries](#libraries). |
| `wasm` | WebAssembly, plus the small JavaScript modules that load it. | A Wasm module instantiated by the result page. | Computation, where real WebAssembly is the point. |

### JavaScript target

The default. The compiler emits one JavaScript module, which the result page runs as a plain script.
It can use the DOM and the [libraries](#libraries) above. See [Standard I/O](#standard-io) for what it
can print and read.

### Wasm target

The compiler emits a WebAssembly module. The result page instantiates it, and the program runs there.
Because it does not run in the page's JavaScript context:

- **No libraries.** The backend is `wasmJs`, so the JS-only libraries are unavailable; only the
  standard library compiles.
- **No DOM.** It is a console program: `println` output appears in the
  [console](../features/console.mdx), and `readLine` reads the
  [standard input](#standard-input). It also has no `System`, unlike the JavaScript target.

```kotlin
fun main() {
    val n = readlnOrNull()?.trim()?.toIntOrNull() ?: 10
    println("counting to " + n)
    for (i in 1..n) {
        if (i % 2 == 0) println(i.toString() + " is even")
    }
    println("sum=" + (1..n).sum())
}
```

This demo runs the program above with the `wasm` target. Its input comes from
`livecodes.kotlin.input`, set in the markup editor, so the console can be rerun with a different
input:

export const kotlinWasmConfig = {
  activeEditor: 'script',
  markup: {
    language: 'html',
    content: `<p>Standard input: <input id="input" value="10" size="4" /> <button id="run">Run again</button></p>
<script>
  // The wasm target reads standard input from \`livecodes.kotlin.input\`.
  livecodes.kotlin.input = document.getElementById('input').value;
  document.getElementById('run').addEventListener('click', () => {
    livecodes.kotlin.run(document.getElementById('input').value);
  });
</script>
`,
  },
  script: {
    language: 'kotlin',
    content: `fun main() {
    val n = readlnOrNull()?.trim()?.toIntOrNull() ?: 10
    println("counting to " + n)
    for (i in 1..n) {
        if (i % 2 == 0) println(i.toString() + " is even")
    }
    println("sum=" + (1..n).sum())
}
`,
  },
  customSettings: {
    kotlin: {
      target: 'wasm',
    },
  },
  mode: 'simple',
  editor: 'auto',
  tools: {
    status: 'full',
  },
};

Switching target at run time works without reloading: each target loads its own compiler, and
switching back reuses the one already loaded, so only the first use of a target pays its download.

## Standard I/O

What is available depends on the target, because the two run in different places: the JavaScript
target runs in the result page's own JavaScript context, while the wasm target runs as a WebAssembly
module.

| | [`js`](#javascript-target) | [`wasm`](#wasm-target) |
| --- | --- | --- |
| `println`, `print` | Console | Console |
| `System.out` / `System.err` / `System.exit` | Available | Not available: unresolved |
| `readLine`, `readln`, `readlnOrNull` | Compile, but read nothing | Read the supplied input |
| [`livecodes.kotlin`](#communication-with-javascript) helpers | — | Available |

### Output

`println` and `print` write to the [console](../features/console.mdx) on both targets.

:::caution Output buffering

Kotlin/JS writes console output through a line buffer: `println` appears immediately, while `print`
without a newline appears only once the line is completed.

:::

`System.out.println` and `System.err.println` are available on the JavaScript target, as they are on
the JVM. `System.exit` is accepted there too, but does not stop the program, because the result page
has already run it as a script.

:::caution `System` is unavailable on the wasm target

Kotlin/Wasm's standard library has no `System` object, so `System.out.println`, `System.err.println`
and `System.exit` do not compile there (`Unresolved reference 'System'`). Use `println` instead.

:::

### Standard input

The wasm target reads standard input with `readLine`, `readlnOrNull` and `readln`. It is pre-supplied
input, not an interactive console: each call returns the next line, and once the input runs out they
return `null` — so `readln` throws, as it does at end of input on the JVM.

```kotlin
fun main() {
    val n = readlnOrNull()?.trim()?.toIntOrNull() ?: 10
    println("sum=" + (1..n).sum())
}
```

The JavaScript target has no console input: those calls compile but read nothing, and `readln` always
throws.

### Communication with JavaScript

With the wasm target, the program runs in the context of the result page, and a few helpers are
available in the browser global `livecodes.kotlin` object:

- `livecodes.kotlin.input`: The standard input passed to the program. Set it before the first run.
- `livecodes.kotlin.loaded`: A promise that resolves when the environment is ready to run.
- `livecodes.kotlin.output`: The standard output from the last run.
- `livecodes.kotlin.error`: The error from the last run, if it failed.
- `livecodes.kotlin.exitCode`: The exit code of the last run.
- `livecodes.kotlin.run`: A function that runs the code with new input. It takes a string as input and
  returns a promise that resolves with an object containing the `output`, `error` and `exitCode`
  properties.

```js
// Before the first run: the program reads this as its standard input.
livecodes.kotlin.input = '12';

// Later, rerun with different input and read the result.
const { output, error, exitCode } = await livecodes.kotlin.run('20');
// output: "sum=210", error: null, exitCode: 0
```

The output also appears in the [console](../features/console.mdx): capturing it does not divert it.

The demo under [Wasm target](#wasm-target) uses this API: its markup sets
`livecodes.kotlin.input` and calls `livecodes.kotlin.run` from a button.

These helpers belong to the wasm target, which the page drives as a module. The JavaScript target's
emitted script runs itself, so there is no run to call again with new input.

## Libraries

The [JavaScript target](#javascript-target) can import common Kotlin libraries, which are downloaded
the first time a program imports one, so a program that imports nothing pays nothing.

```kotlin
import kotlinx.serialization.Serializable
import kotlinx.serialization.json.Json

@Serializable
data class Point(val x: Int, val y: Int)

fun main() {
    println(Json.encodeToString(Point(2, 3)))
}
```

Available: `kotlinx.browser`, `kotlinx.html`, `kotlinx.coroutines`, `kotlinx.collections.immutable`,
`kotlinx.datetime`, `kotlinx.serialization` (including `@Serializable`), `kotlinx.atomicfu` and
`kotlin.test`.

:::note

Each library is fetched on demand, so the first run using one is slower than later runs. The compiler
itself is downloaded and cached separately.

:::

### Coroutines

`kotlinx.coroutines` is available on the JavaScript target: `launch`, `async`, `coroutineScope`,
`delay` and the dispatchers all work, and `suspend fun main()` is supported.

There are no threads in JavaScript, so `runBlocking` does not exist on Kotlin/JS — use `coroutineScope`
inside `suspend fun main()`, or launch from `GlobalScope` and let the page keep running.

```kotlin
import kotlinx.coroutines.*

suspend fun main() {
    coroutineScope {
        for (i in 1..3) {
            launch {
                delay(100L * i)
                println("tick $i")
            }
        }
    }
    println("done")
}
```

`System.currentTimeMillis()` and `Thread.currentThread()` are supplied for the JavaScript target, since
tutorials use them for timing but Kotlin/JS has neither. Because there is one thread, `Thread.currentThread().name`
is `main`.

### Tests

`kotlin.test` is available on the JavaScript target; assertions such as `assertEquals` and `assertTrue`
work, and a failed assertion throws (`AssertionError: Expected <5>, actual <4>.`), which appears in the
[console](../features/console.mdx).

```kotlin
import kotlin.test.*

fun main() {
    assertEquals(4, 2 + 2)
    assertTrue(listOf(1, 2).size == 2)
    println("all assertions passed")
}
```

:::note

The test results appear as console output, not in the Tests pane: that pane runs JavaScript tests written
for [the test runner](../features/tests.mdx), not `kotlin.test` assertions.

:::

## Working with the DOM

Kotlin/JS is not JavaScript with different syntax, and habits from JS or TypeScript often do not
compile. The three that catch people first:

### A trailing lambda cannot be an event handler

The JS style passes the handler last, but Kotlin's `addEventListener` declares `options` last:

```kotlin
// Does not compile: "No value passed for parameter 'callback'"
button.addEventListener("click") {
    count += 1
}
```

Pass the handler as the second argument instead:

```kotlin
import kotlinx.browser.document

fun main() {
    var count = 0

    fun render() {
        document.getElementById("counter")?.textContent = count.toString()
    }

    document.getElementById("counter-button")?.addEventListener("click", {
        count += 1
        render()
    })
    render()
}
```

The lambda is converted to the expected callback type, so no explicit cast is needed. A typed lambda
(`{ _: Event -> … }`) or an explicit `EventListener { … }` also work if you prefer to be explicit.

### Elements are nullable, and `getElementById` returns a platform type

Every `getElementById` result may be absent, so use `?.`. Without it the program does not compile —
which is helpful, but means JS code copied over usually needs `?.` added.

### Kotlin's `document` is the typed DOM, not `dynamic`

`import kotlinx.browser.document` gives the browser a real Kotlin type, so a call must match a real
signature. The alternative — declaring `external val document: dynamic` — compiles anything and is
what makes mismatched calls look fine until run time. Prefer the import.

## Custom Settings

[Custom settings](../advanced/custom-settings.mdx) added to the property `kotlin` configure the
compiler.

### `target`

Which backend the compiler uses: `js` (the default) or `wasm`. See [Targets](#targets) for what each

```json title="Custom Settings"
{
  "kotlin": {
    "target": "wasm"
  }
}
```

## Limitations

Both targets:

- Single file: no Gradle and no multi-file projects.
- The compiler requires a browser with [WasmGC](https://webassembly.org/roadmap/) support
  (Chrome/Edge 119+, Firefox 120+, Safari 18.2+) and `DecompressionStream`.
- No semantic completion or inline analysis (the compiler's Analysis API is not included).

The [JavaScript target](#javascript-target) additionally:

- Supports libraries only from the set listed under [Libraries](#libraries).
- Has no standard input: `readLine` and friends read nothing.
